1. Secure Software Development Mindset

A secure system is not created by adding a security feature at the end. Security decisions must be made continuously throughout the software lifecycle.

Core principle: the SSDLC is iterative. Monitoring, incidents, vulnerability reports, architectural changes and new threats feed back into requirements, design and testing.

2. Stage 1 - Secure Requirements

Requirements define both what a system must do and the security conditions under which it must do it. Security requirements should be measurable and testable.

Requirement typeSecurity-focused questionExampleVerification
FunctionalWhat action must the system perform?An authenticated banking customer can transfer funds to an approved beneficiary.Functional/integration test
ConfidentialityWho is allowed to see the data?Only authorised clinicians can view a patient's clinical record.Access-control testing
IntegrityWho can create or modify the data?A prescription cannot be changed after approval without an authorised amendment workflow.Tampering/authorisation tests
AvailabilityHow resilient must the service be?Critical services have tested failover and recovery mechanisms.Resilience/load/failover tests
AuditabilityCan sensitive actions be reconstructed?Privileged actions generate timestamped audit events.Audit-log verification
PerformanceCan security checks operate at required scale?Authorisation checks complete without unacceptable delay during expected peak usage.Performance test
Secure requirement pattern: “The system shall [perform an action] for [an authorised actor], subject to [a security condition], and shall create [verifiable evidence].”

Measurable security requirements and verification criteria support secure development (OWASP Foundation, 2025; Souppaya et al., 2022).

3. Two Elaborated Realistic Secure-System Case Studies

The following examples are intentionally realistic enough for requirements analysis, threat modelling, UML modelling, secure coding, testing and deployment exercises. They are hypothetical teaching scenarios created for this note, not reports of a particular bank or hospital. Security recommendations draw on the sources cited below; clinical workflow details are illustrative requirements for classroom analysis.

Case Study A - Secure Online Banking and Funds Transfer System

The banking security controls illustrate server-side transaction authorisation and object-level permission checks (OWASP Foundation, n.d.-h; OWASP Foundation, n.d.-a).

Business scenario: A retail bank provides a web and mobile service through which customers can authenticate, view accounts, create beneficiaries and transfer money. Customer-service and fraud staff have separate privileged workflows. The design must protect money and personal data while remaining responsive and highly available.

Primary actors

  • Customer
  • Customer-service officer
  • Fraud/security analyst
  • Bank administrator
  • External payment network

Critical assets

  • Funds and account balances
  • Credentials and MFA factors
  • Personal/customer data
  • Beneficiary details
  • Transactions and audit evidence
  • Session/token material

Trust boundaries

  • User device to Internet
  • Internet to WAF/API gateway
  • Application to identity service
  • Application to database
  • Bank to payment network
  • Operations staff to admin services

Representative end-to-end user story

Select account
→

→

Functional requirements

  1. Enrol a customer and bind approved authentication factors.
  2. Authenticate a customer and establish a time-limited session.
  3. Display only accounts owned by or delegated to that customer.
  4. Add, verify, activate and remove beneficiaries.
  5. Create immediate or scheduled transfers within applicable limits.
  6. Display a confirmation before committing a high-risk transfer.
  7. Generate a unique transaction reference and receipt.
  8. Allow authorised staff to freeze accounts or investigate suspicious activity.
  9. Allow customers to view transaction history and security notifications.

Non-functional and security requirements

  1. Confidentiality: account and identity data are protected in transit and at rest.
  2. Authorisation: every account, beneficiary and transfer request is checked server-side against the authenticated principal.
  3. Integrity: debit/credit posting is atomic; partial transfer states are not permitted.
  4. Authentication: sensitive or anomalous actions can require step-up authentication.
  5. Availability: critical services use resilient deployment, backup and tested recovery.
  6. Auditability: security-sensitive actions create protected, timestamped audit events.
  7. Performance: normal security checks must remain responsive at peak load.
  8. Privacy: logs and support screens expose only data required for the user's role.

Case question: A customer starts a transfer with £100, then modifies the amount field in the browser to £10,000 before submission. Where must the bank enforce the authoritative amount/limit rules?
Answer: on the trusted server side. Client controls are useful for usability but cannot be trusted as a security boundary. The server must validate amount, account ownership, beneficiary status, transfer limit, account state and any step-up-authentication requirement before committing the transaction.
Answer: server-side business validation and authorisation must be authoritative; client-side restrictions are not a security boundary.

Case Study B - Secure Hospital E-Prescribing and Electronic Patient Record System

The hospital scenario applies general access-control and audit principles (OWASP Foundation, n.d.-a; OWASP Foundation, n.d.-c). Clinical safety rules require separate domain validation; these sources support the software-security controls.

Business scenario: Doctors and other authorised clinicians review a patient's electronic record and create medication orders. Pharmacists validate and dispense prescriptions. Some data may need emergency access, but every access must be justifiable, appropriately authorised and auditable because a confidentiality or integrity failure can also become a patient-safety issue.

Primary actors

  • Doctor / prescriber
  • Nurse / authorised clinician
  • Pharmacist
  • Clinical administrator
  • Patient (limited portal)
  • Emergency-access user

Critical assets

  • Patient demographics
  • Diagnoses and clinical notes
  • Allergies and medication history
  • Prescriptions and amendments
  • Clinician identities / roles
  • Audit and safety alerts

Trust boundaries

  • Hospital workstation to application
  • Clinical app to identity/RBAC service
  • Application to clinical database
  • Hospital to pharmacy/service interfaces
  • Patient portal to clinical services
  • Emergency access to protected records

Representative end-to-end clinical story

Clinician login
→
Role/context check
→
Select patient
→
Review allergies
→
Prescribe
→
Safety + authority checks
→
Sign / audit

Functional requirements

  1. Authenticate clinicians, pharmacists and administrators.
  2. Find the correct patient using approved identifiers.
  3. Display records according to role, care relationship and organisational policy.
  4. Review current medication, allergies and relevant clinical history.
  5. Create a prescription with medicine, dose, route, frequency and duration.
  6. Run interaction, allergy and duplicate-therapy checks before signing.
  7. Digitally approve/sign the medication order.
  8. Allow pharmacists to record validation and dispensing status.
  9. Support controlled amendment, cancellation and discontinuation.
  10. Provide controlled emergency/break-glass access when normal access would obstruct urgent care.

Non-functional and security requirements

  1. Confidentiality: users see only records and fields justified by their role/context.
  2. Integrity: signed prescriptions cannot be silently overwritten; amendments are versioned.
  3. Accountability: record views, prescription creation, signing and emergency access are auditable.
  4. Availability: critical clinical functions have downtime/recovery procedures.
  5. Safety: alerts are accurate, understandable and cannot be bypassed silently.
  6. Usability: security controls must not encourage unsafe workarounds during clinical care.
  7. Session security: inactive sessions lock appropriately on shared workstations.
  8. Privacy: sensitive patient data must not leak through logs, error messages or notifications.

Case question: A doctor signs a prescription, but another user later changes the dose by directly calling the API. Which principles have failed?
Answer: object/action authorisation and integrity controls have failed. A signed prescription should have a protected lifecycle. Changes should use an authorised amendment/versioning workflow, be attributable to an actor and produce new audit evidence rather than silently overwriting the original order.
Answer: server-side authorisation, prescription lifecycle integrity, versioning and audit controls are required.

4. Stage 2 - Threat Modelling

Threat modelling asks: What are we building? What can go wrong? What are we going to do about it? Did we do enough?

Assets

Credentials, sensitive data, money, prescriptions, API tokens, encryption keys, logs and service availability.

Attack surface

Login forms, APIs, database queries, file uploads, third-party integrations, admin panels and network boundaries.

Threat categories

Spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege.

Interactive challenge: A logged-in user changes beneficiary_id=204 to beneficiary_id=205. The server trusts the submitted identifier without checking ownership.
Issue: broken object-level authorisation / IDOR-style failure. Hiding identifiers does not fix it. The server must verify that the authenticated principal is authorised for the requested resource and action.
Answer: broken object-level authorisation / IDOR-style failure. The server must enforce resource-level authorisation.

Threat modelling uses application decomposition, threat identification, mitigation and review; data-flow diagrams help identify trust boundaries (OWASP Foundation, n.d.-g).

5. Stage 3 - Secure Design and UML

Security-aware design models make trust assumptions, privilege boundaries, sensitive data and authorisation points visible before coding begins.

Use Case Diagram - Secure Banking

Security review questions: Which use cases require authentication? Which need step-up authentication? Which actions require audit logging? Where is server-side authorisation mandatory?

Correct UML class-box structure: each class is represented by one rectangle divided into three compartments: (1) Class Name, (2) Properties / Attributes, and (3) Methods / Functions. Visibility markers such as + public, - private and # protected may be used when appropriate.
Class Diagram A - Secure Online Banking Domain (Three-Compartment UML Classes)

Reading the model: a Customer owns one or more Accounts, manages zero or more Beneficiaries and creates Transactions. Security-sensitive methods such as authorise(), commit() and freeze() belong inside trusted domain/service logic rather than being controlled directly by browser fields. AuditEvent captures attributable security evidence.

Class Diagram B - Hospital E-Prescribing Domain (Three-Compartment UML Classes)

Reading the model: Clinician access to Patient data is permission/context dependent; a Patient can have multiple Prescriptions; Prescription methods enforce its secure lifecycle; Pharmacist actions update dispensing state through authorised methods; AuditEvent records record-access, signing, amendment, dispensing and emergency-access evidence.

6. Stage 4 - Secure Coding

Unsafe query construction

query = "SELECT * FROM users WHERE name='" + username + "'"

Untrusted input can change the meaning of the SQL statement.

Safer approach

query = "SELECT * FROM users WHERE name = ?" execute(query, [username])

Use parameterised operations, validate business constraints and run with minimal database privilege.

Input

Validate type, range, length, format and business meaning.

Output

Encode data for the destination context (HTML, URL, JavaScript, etc.).

Authorisation

Perform server-side checks on every protected request.

Secrets

Never hard-code production passwords, API tokens or cryptographic keys.

Dependencies

Use maintained components and track vulnerability advisories.

State

Protect sessions, CSRF-sensitive operations and transaction boundaries.

Parameterized queries separate data from SQL syntax, and permissions should be validated on every protected request (OWASP Foundation, n.d.-f; OWASP Foundation, n.d.-a).

7. Complexity Analysis (Big O) and Security

Complexity matters to secure programming because inefficient security checks may become bottlenecks or denial-of-service opportunities.

O(1)constant
O(log n)logarithmic
O(n)linear
O(n log n)efficient sorting
O(n²)quadratic
Secure-programming operationTypical complexityWhy it matters
Hash-table lookup for session or roleO(1) averageFast repeated security decisions.
Binary search in sorted rule setO(log n)Scales well as policies grow.
Scan n audit eventsO(n)May need indexing or streaming at high volume.
Sort n security alertsO(n log n)Usually acceptable for large collections.
Compare each event with every other eventO(n²)Can become an availability/performance risk.
Important: efficient code is not automatically secure code. Big O describes growth in computational work; security also requires correct validation, authorisation, cryptography, state management and failure handling.

Asymptotic analysis describes how resource use grows with input size (Massachusetts Institute of Technology, 2011). Uncontrolled resource consumption can affect availability (MITRE, n.d.).

8. Secure Error Handling

Poor production response

HTTP 500 DatabaseError: connection failed Server: db-prod-03 User: admin_service /path/app/payment.py line 241

Secure handling

User response: "We could not complete this request. Reference: X7K92." Protected server log: request_id, actor_id, event_type, timestamp, diagnostic details
  • Do not expose stack traces, SQL, internal paths or secrets.
  • Catch expected errors at appropriate trust boundaries.
  • Use transactions to prevent partially completed sensitive operations.
  • Use generic authentication failures where account enumeration is a concern.
  • Apply throttling/rate limits to repeated error-producing requests where appropriate.
  • Use correlation/reference IDs to support diagnosis without exposing internals.

Unexpected errors should produce a generic external response while diagnostic details are recorded securely; sensitive data should be excluded from logs (OWASP Foundation, n.d.-b; OWASP Foundation, n.d.-c).

9. Stage 5 - Security Testing

Security unit tests

Boundary values, validation, role checks and error paths.

SAST

Analyse source/bytecode for insecure patterns.

SCA

Identify vulnerable or outdated third-party components.

DAST

Probe the running application externally.

Fuzzing

Use malformed and unexpected inputs to expose weaknesses.

Penetration testing

Authorised adversarial testing of realistic attack paths.

Teaching point: passing normal functional tests does not prove security. A transfer function may work correctly for its owner while still allowing another authenticated user to access or modify it.

Combine security verification methods and test access control, input handling and failure paths (OWASP Foundation, n.d.-e; Souppaya et al., 2022).

10. Stage 6 - Secure Deployment

  • Disable debug mode and unnecessary services.
  • Harden production configuration.
  • Use TLS and protected internal communications.
  • Inject secrets from a secret-management mechanism.
  • Use least-privileged service identities.
  • Scan build artefacts, containers and dependencies.
  • Protect CI/CD credentials and branch/release controls.
  • Use controlled approvals for production changes.
  • Maintain tested backup, rollback and recovery processes.
  • Verify logging and alerting before go-live.

Protect release artefacts, configure software securely and maintain release integrity (Souppaya et al., 2022; OWASP Foundation, 2025).

11. Stage 7 - Monitoring and Maintenance

  • Collect meaningful security telemetry and protect the logs themselves.
  • Detect abnormal authentication, authorisation and privilege activity.
  • Patch vulnerable libraries, platforms and infrastructure.
  • Review privileged access and inactive accounts periodically.
  • Repeat threat modelling when architecture, data or trust boundaries change.
  • Investigate incidents and convert lessons learned into new requirements and tests.

Vulnerability response and protected application logging support ongoing security maintenance (Souppaya et al., 2022; OWASP Foundation, n.d.-c).

13. Interactive Classroom Activities

Activity 1 - Requirements Challenge

Choose banking or e-prescribing. Write five functional requirements and five measurable security/non-functional requirements. Label each security requirement as mainly supporting confidentiality, integrity, availability, accountability or privacy.

Activity 2 - Threat Modelling

Draw a data-flow diagram containing user, application, authentication service and database. Mark trust boundaries. Identify at least six threats and one mitigation per threat.

Activity 3 - UML Security Review

Add an Administrator actor to the banking Use Case diagram. Decide which actions require stronger authentication, separation of duties and mandatory auditing.

Activity 4 - Complexity Challenge

An intrusion-monitoring function compares every one of n login events with every other login event. Determine the time complexity and propose indexing, grouping or streaming approaches that reduce unnecessary work.

Activity 5 - Error Handling

A login API returns “User Karim exists but password is incorrect.” Explain the security concern and redesign both the user-facing response and the protected internal log entry.
